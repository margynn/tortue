# UDP Tracker Protocol

## Introduction

To discover peers in a swarm, a client announces its existence to a tracker. Traditionally, this uses HTTP with parameters such as `info_hash`, `key`, `peer_id`, `port`, `downloaded`, `left`, `uploaded`, and `compact`.

The response returns a list of peers (host and port) and additional metadata. Although requests and responses are small, TCP introduces overhead due to connection setup and teardown.

## Overhead

HTTP over TCP introduces overhead at multiple layers:

- Ethernet: 14 bytes per packet
- IP: 20 bytes per packet
- TCP: 20 bytes per packet
- HTTP: variable

A typical announce uses ~1206 bytes. UDP reduces this to ~618 bytes (~50% reduction), improving scalability for trackers.

## UDP Connections / Spoofing

UDP allows IP spoofing, so a handshake is required using a `connection_id`.

- Client requests connection_id
- Tracker responds with connection_id
- Client must reuse it

Validity:

- Client: 1 minute
- Tracker: accepts up to 2 minutes

## Timeouts

Retry formula: 15 \* 2^n seconds (n ≤ 8, max 3840s)

Client must retransmit and refresh connection_id when expired.

## Protocol

All values are big-endian. Packet sizes may vary.

## Connect

### Request

| Offset | Size   | Name           | Value         |
| ------ | ------ | -------------- | ------------- |
| 0      | 64-bit | protocol_id    | 0x41727101980 |
| 8      | 32-bit | action         | 0             |
| 12     | 32-bit | transaction_id |               |

### Response

| Offset | Size   | Name           |
| ------ | ------ | -------------- |
| 0      | 32-bit | action         |
| 4      | 32-bit | transaction_id |
| 8      | 64-bit | connection_id  |

## Announce (IPv4)

### Request

| Offset | Size   | Name           |
| ------ | ------ | -------------- |
| 0      | 64-bit | connection_id  |
| 8      | 32-bit | action (1)     |
| 12     | 32-bit | transaction_id |
| 16     | 20B    | info_hash      |
| 36     | 20B    | peer_id        |
| 56     | 64-bit | downloaded     |
| 64     | 64-bit | left           |
| 72     | 64-bit | uploaded       |
| 80     | 32-bit | event          |
| 84     | 32-bit | IP (0)         |
| 88     | 32-bit | key            |
| 92     | 32-bit | num_want (-1)  |
| 96     | 16-bit | port           |

### Response

| Offset | Size   | Name           |
| ------ | ------ | -------------- |
| 0      | 32-bit | action (1)     |
| 4      | 32-bit | transaction_id |
| 8      | 32-bit | interval       |
| 12     | 32-bit | leechers       |
| 16     | 32-bit | seeders        |
| 20+    | peers  |                |

## Scrape

### Request

| Offset | Size   | Name           |
| ------ | ------ | -------------- |
| 0      | 64-bit | connection_id  |
| 8      | 32-bit | action (2)     |
| 12     | 32-bit | transaction_id |
| 16+    | 20B    | info_hash      |

### Response

| Offset | Size   | Name                       |
| ------ | ------ | -------------------------- |
| 0      | 32-bit | action                     |
| 4      | 32-bit | transaction_id             |
| 8+     | 32-bit | seeders/completed/leechers |

## Errors

### Response

| Offset | Size   | Name           |
| ------ | ------ | -------------- |
| 0      | 32-bit | action (3)     |
| 4      | 32-bit | transaction_id |
| 8      | string | message        |

## Notes

- IPv6 uses 18-byte peer entries
- No fixed packet size
- Supports extensions (see BEP 41)
